# 技术细节演进与设计理由 (Architecture Evolution & Design Rationale)

本文档记录 Nexus 系统的演进历程、设计决策依据与性能测评指标。

---

## 1. 架构演进路线

1. **v1.0 (Direct SSH / Webhook)**:
   - 依赖暴露 SSH 端口或依赖 HTTP 同步连接。受限于 30 秒 HTTP 超时壁垒，无法运行长时任务。
2. **v2.0 (Supabase REST + CAS Pull Protocol)**:
   - 引入 Supabase Cloud REST 数据库，采用 `pending` -> `running` -> `completed` 异步 CAS 锁状态机，彻底规避超时问题。
3. **v3.0 (FastMCP Dual Transport Architecture)**:
   - 引入 FastMCP 协议层 (`mcp_server/`)。
   - 实现 **STDIO 模式**（本地 CLI）与 **HTTP/SSE 模式**（`nexus.bings.app/sse`）双模传输。

---

## 2. 设计理由 (Design Rationale)

### 为什么选择 FastMCP + Supabase Cloud？
- **可靠性**: Supabase Cloud 保证节点心跳与命令在云端持久化，即使物理机器临时断网或关机，任务也不会丢失。
- **扩展性**: FastMCP 为 ChatGPT、Claude、Cursor、Antigravity 等任意现代 AI 客户端提供了标准化的 Tool 交互接口。

| 指标 | 测量值 | 评级 |
| :--- | :--- | :--- |
| **Command Enqueue Latency (POST /commands)** | < 18 ms | 极优 |

## 4. v2.5-regional 最终架构决策

### 4.1 控制面从单中枢演进为区域 Broker

最终架构采用 Oracle Global API + Oracle EU Broker + ThinkCenter CN Broker。Global API 负责统一入口与区域路由；Broker 负责热队列、lease 和完成回执；Supabase 降级为设备目录、心跳与审计镜像。

### 4.2 目标不可变与区域故障转移

任务使用规范 `target_device`。故障转移只允许在 EU/CN Broker 之间改变传输路径，禁止把命令改派其他设备。每个任务带 UUID、idempotency key、lease owner、attempt；Agent 本地 execution ledger 抑制重复执行。

### 4.3 Windows worker 超时修复

Victus Agent 为 Windows 子进程创建独立进程组；超时后终止完整进程树，并对第二次 `communicate()` 设置 5 秒上限，避免后代进程继承 stdout/stderr 后永久占用 worker。

### 4.4 常用浏览器登录态复用

主浏览器通道不复制 Cookie 或密码。Windows Chrome Profile 3 安装 Playwright Extension，Windows Playwright MCP 与 Victus WSL Adapter 通过扩展授权连接。`agent-browser + F盘隔离 Profile` 保留为 fallback。

### 4.5 Provider 专用完成检测

Gemini 使用页面稳定检测；Claude 使用新增 assistant/article 节点与 streaming 状态检测。不能用整个 `main.innerText()` 是否稳定作为 Claude 完成依据，否则动态 UI 会造成假超时。
